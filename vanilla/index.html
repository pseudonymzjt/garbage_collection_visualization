关于本游戏

本游戏通过六道精心设计的关卡，带您深入理解 Java 虚拟机（JVM）垃圾回收机制 以及 Java 开发中最经典的 6 种内存泄漏场景。

基本操作

  • 拖拽节点：调整内存对象在画布上的位置
  • 连线模式：点击「连线模式」后依次点击两个节点，建立引用关系
  • 删除连线：点击「删除连线」后依次点击两节点，切断引用
  • 右键节点：删除节点（沙盒模式）
  • 运行 GC：选择「标记-清除」或「引用计数」算法回收垃圾

节点颜色说明

  • 绿色 — GC Root（根可达对象）
  • 橙色 — 事件源 / 发布者
  • 紫色 — JVM 内部对象
  • 灰色 — 普通堆内存对象

提示：右侧 Java 代码面板会随您的操作实时变化——连线存在时泄漏代码高亮（黄色），切断后变为修复代码（红色删除线）。

垃圾回收算法说明

本游戏实现了两种经典的垃圾回收算法，理解它们的差异是本工具的核心学习目标：

标记-清除（Mark-Sweep）

原理：从 GC Root（绿色节点）出发，沿引用连线做广度优先遍历，标记所有可达对象；然后清除所有未被标记的对象。
动画表现：黄色光芒从根节点向外扩散 → 被扫到的对象变黄（标记）→ 未被标记的节点缩小淡出（清除）。
优势：能正确回收循环引用（L2）——因为从 Root 遍历不到的闭环对象不会被标记。
劣势：需要 STW（Stop-The-World）暂停所有应用线程；会产生内存碎片。

引用计数（Reference Counting / RC）

原理：每个对象维护一个 rc（引用计数），记录有多少个对象指向它。当 rc 降为 0 时立即被回收。
动画表现：节点上的 rc: N 徽章实时反映入边数量 → 删除节点时级联递减相邻节点的 rc。
优势：回收可增量执行，无需 STW 暂停；适合实时性要求高的场景。
劣势：无法处理循环引用（L2 演示此缺陷）——互相引用的对象即使外部不再可达，rc 也永远 ≥ 1；且每次赋值都要更新计数，有一定性能开销。

主流 JVM（HotSpot）选择可达性分析（类似 Mark-Sweep 的遍历思路）而非引用计数作为核心 GC 方案，正是因为循环引用的根本性缺陷。但你可以在本游戏的 L2 中亲手验证这一点。

L1：静态集合

在 Java 程序中，静态变量属于类本身，而不是某个具体的对象。静态变量会一直存在，直到程序结束。加载这个类的类加载器在程序运行期间不会被销毁，所以静态变量指向的对象会被垃圾回收器当作“根对象”（不能被回收的起点）。在 CacheManager 类的 process() 方法中，方法内部创建了一个临时变量 tempData，它指向一个 100MB 的大对象。这个方法把该对象加入了一个静态集合 cache。方法执行完后，临时变量就消失了，但静态集合还一直存在。静态集合仍然牢牢地引用着那个大对象。垃圾回收器从根对象出发查找时，会顺着“类加载器 → 静态集合 → 大对象”这条路径找到它，认为它还在使用中。于是，这个本应被清理的临时数据就一直留在内存里，导致内存占用越来越高。

L2：循环引用

有一种简单的垃圾回收算法叫做“引用计数法”。它记录每个对象被引用的次数，次数为零就回收。现在有两个对象 b 和 c，它们互相引用（比如 b.next = c; c.next = b）。就算程序里已经没有其他变量再指向 b 或 c，它们两个内部仍然互相指着对方。所以每个对象的引用次数始终是 1，永远不会变成 0。引用计数法无法识别这种情况，这两个对象就永远无法被回收。这就是“循环引用”问题。Java 虚拟机没有采用引用计数法，而是采用了另一种方法：从一些固定的根对象（比如正在运行的线程、静态变量）出发，沿着引用链去寻找还在使用的对象。找不到的对象才会被回收。这样，互相引用但外部没有联系的对象就能被正确清理掉。

L3：堆内存强引用

在 Java 中，只要一个对象还被至少一个地方强引用着，垃圾回收器就不能把它清理掉。有时候，一个大对象可能同时被好几个地方引用。比如，一个大的缓冲区 bigBuffer 既被 HeavyComp 对象引用，又被另一个还在活跃的组件直接引用。这时，即使你切断了 HeavyComp 对 bigBuffer 的引用，因为还有另一条引用路径存在，这个缓冲区仍然无法被回收。要避免这种内存问题，必须找出所有指向这个对象的引用，确保在该对象不再需要时，每一条引用都被彻底切断。

L4：监听器未注销

在 Java 中，如果一个类被定义为另一个类的“非静态内部类”或“匿名内部类”，那么这种内部类的对象会自动持有它外部类对象的引用（可以理解为内部类知道自己在哪个外部对象里创建）。当 HeavyComponent 创建了一个监听器对象（匿名内部类），并把这个监听器注册到一个长期存在的全局组件 EventPublisher 上时，就会形成一条引用链：EventPublisher → 监听器 → HeavyComponent。等到 HeavyComponent 不再需要使用时，如果你只是让程序不再直接引用它，却没有从 EventPublisher 上注销这个监听器，那么 EventPublisher 仍然会通过监听器间接引用着 HeavyComponent。垃圾回收器顺着这条链找到它，认为它还在使用中，于是 HeavyComponent 及其内部的大数据对象都无法被回收，造成内存泄漏。

L5：ThreadLocal 遗留

每个线程对象内部都有一个专门的小字典（叫做 ThreadLocalMap），用来存放线程私有的数据。字典里的每一个条目，键是 ThreadLocal 对象（这个键的引用比较弱，不影响垃圾回收），值是你存入的具体数据（这个值的引用是强引用，会阻止回收）。在 Web 应用等高并发环境下，线程通常由线程池管理，线程会长期存活并反复使用。当一个线程在处理请求时，向 ThreadLocal 中存入了 80MB 的数据，如果在请求处理结束后没有显式调用 remove() 方法删除这条数据，那么即使那个 ThreadLocal 键已经被回收，这个线程的字典里仍然用强引用保留着那个 80MB 的数据。因为线程本身就是一个根对象（不会被回收），所以这份数据会一直留在内存里，即使线程被归还到线程池供后续请求使用。这就导致了因线程复用而产生的内存泄漏。

L6：未取消的后台 Timer

当你创建一个 java.util.Timer 对象时，Java 虚拟机会在后台启动一个专门的工作线程（叫做 TimerThread）来执行定时任务。这个工作线程一旦启动就会一直运行，并且它本身属于根对象，不会被垃圾回收。该线程内部有一个任务队列，里面存放着需要执行的 TimerTask 任务对象。如果你的业务类 Service 在停止服务时没有调用 timer.cancel() 来终止这个后台线程，那么线程会永远存活。如果这些 TimerTask 任务被定义成内部类，它们会自动持有外部业务类对象的引用。这样一来，垃圾回收器会顺着“后台线程（根对象） → 任务队列 → 任务对象 → 外部业务对象”这条引用链，认为所有这些对象都还在使用中。于是，你的业务对象无法被回收，内存也就无法释放。
